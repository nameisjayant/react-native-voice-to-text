How it works

The whole voice search flow, in one component

Uses Android's SpeechRecognizer and iOS's SFSpeechRecognizer, so there are no API keys, servers or extra dependencies.

1

Tap the mic

The user taps the mic inside your search bar. Permission is requested on the spot if needed.

2

Dialog listens

"Listening… Speak now" opens. The ring follows the voice level and the words appear live.

3

Silence stops it

After a short pause with no new words, the session ends and the dialog closes by itself.

4

Search runs

The recognised text lands in your search field and onSearch fires.

Silence auto-stop

Ends the session after a configurable pause. The timing lives in JavaScript, so iOS and Android behave the same.

Every part themeable

Colours, sizes, font, texts, style overrides, or render props that replace the icon or the whole dialog.

Headless hook

useSpeechToText handles permissions, silence detection and cleanup. Bring your own UI.

Any locale

Pass a BCP-47 tag like 'en-US' or 'hi-IN'. Defaults to the device language.

On-device mode

Set onDevice to prefer offline recognition where the platform supports it.

TurboModule

Built for the New Architecture with codegen. Kotlin on Android, Objective-C++ on iOS.

Installation

Two steps on iOS, none on Android

Add the package

terminal
npm install @nameisjayant/react-native-voice-to-text
# or
yarn add @nameisjayant/react-native-voice-to-text

cd ios && pod install
Use a real device. Speech recognition needs a recognition service (the Google app on Android). Most emulators and simulators don't have a working microphone or recognizer.

iOS: add usage descriptions

Both keys go in Info.plist. iOS shows these strings in the permission prompts.

ios/YourApp/Info.plist
<key>NSMicrophoneUsageDescription</key>
<string>The microphone is used to search by voice.</string>
<key>NSSpeechRecognitionUsageDescription</key>
<string>Speech recognition converts what you say into search text.</string>

Android: nothing to do

The library's manifest adds RECORD_AUDIO and the RecognitionService package-visibility query. The runtime permission prompt appears when listening starts.

Usage

Pick how much the library does for you

Four entry points, from a drop-in search bar down to the raw native module. Each one is built on the next.

A complete search field. Keyboard submit and voice results both call onSearch.

SearchScreen.tsx
import { VoiceSearchBar } from '@nameisjayant/react-native-voice-to-text';

const [query, setQuery] = useState('');

<VoiceSearchBar
  value={query}
  onChangeText={setQuery}
  onSearch={(text) => runSearch(text)} // keyboard submit or voice result
  placeholder="Search restaurants"
/>;

Keep your own search bar. Drop in MicButton and open the dialog yourself.

SearchScreen.tsx
import { MicButton, VoiceSearchDialog } from '@nameisjayant/react-native-voice-to-text';

const [open, setOpen] = useState(false);

<View style={styles.searchBar}>
  <TextInput value={query} onChangeText={setQuery} />
  <MicButton onPress={() => setOpen(true)} />
</View>

<VoiceSearchDialog
  visible={open}
  onResult={(text) => {
    setQuery(text);
    runSearch(text);
  }}
  onClose={() => setOpen(false)}
/>

Build any UI you like. The hook handles permissions, silence detection and cleanup. It also returns isListening.

MyVoiceUI.tsx
import { useSpeechToText } from '@nameisjayant/react-native-voice-to-text';

const { status, transcript, volume, error, start, stop, cancel } = useSpeechToText({
  locale: 'en-US',
  silenceTimeout: 1500,
  onResult: (text) => setQuery(text),
});

// status: 'idle' | 'starting' | 'listening' | 'processing' | 'error'
// volume: mic level 0..1 while listening

Direct access to the native recognizer. Only one session runs at a time; starting a new one cancels the previous.

speech.ts
import { SpeechToText } from '@nameisjayant/react-native-voice-to-text';

await SpeechToText.isAvailable();
await SpeechToText.requestPermissions();
const sub = SpeechToText.onResult(({ value, isFinal }) => {});
await SpeechToText.start({ locale: 'en-US' });
await SpeechToText.stop();   // final result follows
await SpeechToText.cancel(); // no result
sub.remove();

Behaviour

When does listening stop?

Three timers decide. They work on VoiceSearchDialog, the search bar's dialogProps, and useSpeechToText.

0 s · mic opensfirst wordlast wordstops
waiting ≤ 6 s
"spicy ramen near me"
quiet 2 s
onResult(text)
initialSilenceTimeout6,000 msHow long to wait for the user to start speaking.
silenceTimeout2,000 msTime without new words, after speech started, before it stops.
maxDuration60,000 msHard cap on one session. 0 turns it off.
idle→ starting→ listening→ processing→ idle or error

Tapping the mic while listening finishes immediately. Tapping it after an error or no-speech starts a retry.

Customising the UI

Restyle it, translate it, or replace it

Theme values and texts cover most apps. Style props and render props cover the rest.

Theme, position and texts

theme + texts
<VoiceSearchDialog
  visible={open}
  onResult={setQuery}
  onClose={() => setOpen(false)}
  position="bottom"          // 'center' (default) | 'bottom' sheet
  animationType="slide"      // 'fade' (default) | 'slide' | 'none'
  theme={{
    backgroundColor: '#14112B',
    primaryColor: '#6C4DFF',
    pulseColor: 'rgba(108, 77, 255, 0.3)',
    borderRadius: 28,
    micSize: 84,
    fontFamily: 'Inter-Regular',
  }}
  texts={{ listening: 'Escuchando…', speakNow: 'Habla ahora', cancel: 'Cancelar' }}
/>

defaultVoiceSearchTheme (dark) and lightVoiceSearchTheme are exported, so you can spread one and change a few values.

Replace parts of the dialog

render props
// Your own icon inside the mic circle
<VoiceSearchDialog
  renderMicIcon={({ size, color }) => <Icon name="mic" size={size} color={color} />}
/>

// Your own dialog content; the library still
// handles listening and silence detection
<VoiceSearchDialog
  renderContent={({ status, transcript, volume, stop, retry, cancel }) => (
    <MyListeningCard
      status={status}
      text={transcript}
      level={volume}
      onStop={stop}
      onCancel={cancel}
    />
  )}
/>

renderContent also receives error, noSpeech, theme and texts.

Platform notes

Good to know before you ship

AndroidThe system recognizer also ends sessions on its own silence detection, which can be shorter than a long silenceTimeout. The timeout is passed as a hint, but some devices ignore it.
iOSiOS has no built-in endpointing. The silenceTimeout is what ends the session.
BothOnly one recognition session can run at a time. Starting a new one cancels the previous.
